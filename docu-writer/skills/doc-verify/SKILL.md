# 문서 검증

검증은 판단이 아니라 **스크립트**입니다. 같은 파일에는 언제나 같은 결과가 나와야 하므로 모델이 결과를 해석해 통과시키지 않습니다. 이 문서가 스크립트의 명세입니다. 스크립트를 고칠 때는 이 문서를 먼저 고칩니다.

## 실행

```bash
# 1. 렌더 — DOCX·PPTX·MD. HWPX는 아래 「HWPX 렌더」로 대신합니다.
uv run "${CLAUDE_SKILL_DIR}/scripts/render.py" <결과 파일> .docu-writer/render/

# 2. 검증
uv run "${CLAUDE_SKILL_DIR}/scripts/doc_verify.py" \
  --profile .docu-writer/profile.yaml \
  --source <견본> --expect-sha256 <①에서 기록한 값> \
  --output <결과 파일> \
  --placeholders .docu-writer/placeholders.yaml \
  --pages-dir .docu-writer/render/ \
  --out-dir .docu-writer/verify/
```

두 스크립트 모두 PEP 723 인라인 의존성을 적고 `uv run`으로 Python 3.13에서 돕니다. 모드는 프로파일 `mode`에서 읽습니다. `--placeholders`는 자리표시가 없으면 생략합니다.

| 종료 코드 | 뜻 | 할 일 |
|---|---|---|
| 0 | 통과 (`warn`·`skip`만 있음) | 요약을 ⑦ 리뷰어에게 넘깁니다 |
| 1 | 차단 (`fail`이 하나 이상) | 실패한 검사를 ⑤에서 고치고 다시 실행합니다 |
| 2 | 사용법·환경 오류 | 파일·프로파일이 없거나, 지원하지 않는 형식이거나, 렌더 도구(soffice·pandoc)가 없습니다 |

### 신규 모드 (`mode: new`)

2단계 `newdoc-workflow`가 만든 문서는 견본이 없습니다. 같은 스크립트가 프로파일 `mode: new`로 분기합니다(설계서 §9).

- **`--source`·`--expect-sha256`은 선택입니다.** `mode: new`에서 둘 다 없어도 사용 오류가 아닙니다. 둘 중 하나만 주면 사용 오류(종료 코드 2)입니다. 다른 모드에서는 지금처럼 필수입니다.
- **생략하는 검사.** `hash`·`residue`·`scope`·`fields`는 `skip`이며 detail에 「신규 모드」를 적습니다. 원본 보호는 ⑥의 `shasum -c .docu-writer/materials.sha256`(참고 자료·테마 파일)이 맡습니다.
- **`markup`.** 견본이 없으므로 「견본에 같은 꼴이 있으면 뺀다」는 예외 없이 모든 표지를 봅니다. MD 출력은 신규 모드에서도 `skip`입니다(아래 표 참고).
- **`h:` anchor.** 섹션 위치는 결과 문서에서 제목 글이 `h:"…"`의 글과 같은 문단(공백을 빼고 비교)으로 찾습니다. 앞에 붙은 글머리표(`□`·`○` 등, 뒤에 공백이 있을 때)와 장 번호(`Ⅰ.`·`1.`·`1 `·`가.`)는 비교에서 뺍니다. 결과에 제목 스타일 문단(DOCX `Heading N`, MD `#` 제목)이 하나라도 있으면 섹션마다 제목 문단(제목 스타일·`Title`, PPTX 슬라이드 제목)을 먼저 봅니다. 맞는 제목 문단이 있으면 그것만 셉니다. 본문의 「○ 현황」이나 목차 줄 「1. 추진 배경」이 제목 자리를 가로채지 않게 하기 위해서입니다. 맞는 제목 문단이 없으면(그 섹션 제목만 일반 스타일로 쓴 경우) 일반 문단을 글이 똑같을 때만(번호·글머리표를 빼지 않고) 셉니다. 그래서 고친 제목이 본문 줄 「현황」과 우연히 똑같으면 그 줄을 섹션 시작으로 잡을 수 있습니다. 제목 스타일이 없는 문서(HWPX 등)는 모든 문단이 후보이므로 제목용 글머리표(`□■◆◇▶▷`)만 빼고 본문 목록 부호(`○●◎•▪`)는 남깁니다(이런 문서에서 「○ 현황」처럼 목록 부호로 쓴 제목은 본문 목록 줄과 가를 수 없어 못 찾음으로 두고 섹션 분량을 skip합니다). PPTX 제목이 여러 줄이면 줄을 이은 글로 비교합니다. 표 안 제목(HWPX 띠 표)도 원래 글로 번호를 찾습니다. 같은 글이 앞 섹션 제목보다 먼저 나오면(요약·목차 줄) 그 뒤 처음 맞는 문단을 그 섹션 시작으로 씁니다. 이렇게 뒤로 찾은 문단은 본문 줄일 수 있어 앞 섹션 끝으로는 쓰지 않습니다(앞 섹션 분량은 그 섹션을 못 찾았을 때처럼 다음 섹션까지 잽니다). 못 찾은 섹션은 `length`의 섹션 분량을 `skip`으로 두고 detail에 적습니다.
- **빈 토큰.** `design.type.*`·`design.color`·`styles_allowed`가 비어 있으면 그 항목은 비교하지 않습니다(`r4_headings`·`r5_tokens`는 비교할 것이 하나도 없으면 `skip`. `r5_tokens`의 이 규칙은 모든 모드에 적용됩니다. 견본에서 뽑은 토큰이 비어 있을 때도 같습니다). MD는 서체 정보가 없으므로 지금처럼 `skip`입니다.
- `design.route`는 검사하지 않습니다(`profile_extract.py check`가 봄). 종료 코드 규약과 `report.json`의 13개 id는 그대로입니다.

## 렌더 (`render.py`)

| 형식 | 경로 |
|---|---|
| DOCX·PPTX | `soffice --headless --convert-to pdf` → pymupdf로 쪽별 PNG(150dpi) |
| MD | `pandoc` → DOCX → 위와 같음 |
| HWPX | 스크립트가 렌더하지 않습니다. 아래 「HWPX 렌더」 |

`<out-dir>`에 `page_001.png …`와 `pages.json`(`[{"page": 1, "text": "…"}]`, 쪽별 글)을 씁니다. 쓰기 전에 `<out-dir>` 바로 아래의 `page_*`와 `pages.json`만 지웁니다. 하위 디렉터리(`source/`)는 건드리지 않습니다. 이전 렌더가 쪽 수가 더 많았을 때 남은 쪽이 `length`·`r1_tables`를 흐리지 않게 하기 위해서입니다. 쪽별 글은 PDF에서 pymupdf `get_text`로 읽습니다.

**글꼴.** `render.py`는 LibreOffice 전용 프로필의 `user/fonts/`에 글꼴 폴더 링크를 둡니다(macOS: `/System/Library/Fonts`·`/Library/Fonts`·`~/Library/Fonts`, 그리고 `DOCU_WRITER_FONT_DIRS`에 `:`로 나눠 적은 폴더). macOS의 LibreOffice는 headless 변환에서 시스템 글꼴을 못 찾고 내장 Latin 글꼴로만 그리는 일이 있어, 링크가 없으면 한글이 빈 글리프로 찍히고 `pages.json` 글만 멀쩡합니다. 변환한 PDF에서 내장 글꼴에 없는 글자가 그 글꼴로 찍혔으면 PNG를 쓰지 않고 종료 코드 2로 멈춥니다. 이때 메시지에는 글꼴 이름과 글자 종류(한글·한자·기타)별 개수(`한글 12자, 기타 3자`)만 내고 글자는 보이지 않습니다. 내장 글꼴인지는 굵기·기울기 꼬리를 뗀 글꼴 가족 이름 전체로 맞춥니다(`DejaVuSans-Bold`는 `DejaVu Sans`와 한 가족, `DejaVuSansMono`는 다른 가족). 다시 실행하면 이전 글꼴 링크를 지우고 새로 겁니다. 한글 글꼴이 든 폴더를 `DOCU_WRITER_FONT_DIRS`에 적고 다시 실행합니다.

**HWPX 렌더.** kordoc은 MCP 도구라 스크립트에서 부를 수 없습니다. 메인 대화가 `format-hwpx` 「렌더 (⑥)」의 명령 그대로 이전 쪽을 지우고, `render_document(format: "svg", pages: "1-N", output_path: docu-writer-out/page.svg)`와 `format: "png"`를 같은 디렉터리에 낸 뒤 `.docu-writer/render/`로 옮깁니다(kordoc은 숨김 경로에 쓰지 않음). `doc_verify.py`는 `pages.json`이 없으면 `page_*.svg`(kordoc은 여러 쪽이면 `page_page_NNN.svg`, 한 쪽이면 `page.svg`로 냄)의 `<text>` 요소에서 쪽별 글을 읽습니다. 둘이 섞여 있으면 이전 렌더가 남은 것이므로 사용 오류로 멈춥니다. 조판 캐시가 없는 HWPX(AI가 만든 파일)는 근사 렌더이므로 R1·R3 판정은 ⑧에서 「한컴에서 확인 권장」을 붙입니다.

## 검사 항목

| id | 검사 | 모드 | 판정 |
|---|---|---|---|
| `hash` | 견본 sha256이 `--expect-sha256`과 같음 | 모두 | 다르면 `fail` (CRITICAL: 원본이 바뀜) |
| `residue` | 프로파일 `sample_text`의 문구가 결과에 남았는가 | sample | 남으면 `fail`. `○○`만 있는 토큰은 비교에서 뺍니다 |
| `markup` | 마크다운 표지(`> ` 인용, `# ` 제목, `**굵게**`, `\` 탈출, `| … |` 표 줄)가 결과 글에 글자로 남았는가 | 모두 | 남으면 `fail`. 견본에 같은 꼴이 있으면 그 종류는 문서의 글로 보고 뺍니다 (kordoc `patch_document`가 요약 상자 앞에 `> `를 남긴 사례). **MD 출력은 어느 모드든 `skip`**입니다 — 마크다운이 곧 출력 형식이라 `**강조**`·`> 인용`·`| … |`가 모두 정상 문법입니다. 줄 머리 표지(`> `·`# `·`| … |`)는 문단 안 줄바꿈(DOCX 줄 나눔, 여러 문단 표 칸) 뒤 줄에서도 찾습니다. `> 10 mg/L`·`> 0.5%`처럼 `> ` 뒤가 수치이면 비교식으로 보고 빼지만, `> 1. `·`> 2) `처럼 목록 번호가 오면 인용 표지로 봅니다. Windows 경로(`C:\…`·`\\서버\…`), 서명란 `___서명___`, `__init__` 같은 식별자는 표지로 보지 않습니다. 여러 문단 표 칸은 칸 글과 문단 글이 겹쳐 읽히므로 같은 글을 한 번만 셉니다 |
| `placeholder` | 자리표시 목록의 항목마다 `expect` 글이 결과에 있는가. `locator`를 풀 수 있으면 그 위치 안에서 찾음 | 모두 | 없으면 `fail` (kordoc이 `○`를 먹었을 수 있음) |
| `fields` | 프로파일 `fields`마다 칸이 채워졌거나 자리표시 목록에 있는가, `constraint`를 지키는가 | form | 빈칸·위반이면 `fail` (보고에는 칸 값 대신 글자 수만 냄) |
| `scope` | 프로파일 `update.sections` 밖 문단이 견본과 같은가. 섹션 범위는 `anchor`부터 다음 섹션 `anchor` 앞까지 | update | 다르면 `fail` |
| `r4_headings` | 같은 수준 제목의 (서체, 크기, 굵기)가 하나뿐이고 `design.type.hN`과 같은가 | 모두 | 다르면 `fail` |
| `r5_tokens` | 결과가 쓴 서체·크기·색·스타일 이름이 프로파일 토큰과 `styles_allowed` 안인가 | 모두 | 밖이면 `fail` |
| `r6_numbering` | 줄 머리 번호 부호가 `structure.numbering` 안인가, 같은 수준에 부호가 섞이지 않았는가 | 모두 | 어기면 `fail`. `numbering`이 있는데 글에 부호가 없으면 `skip`(자동 번호) |
| `table_header` | 모든 표의 머리행 서식(굵기·바탕색)이 같은가 | 모두 | 다르면 `fail` |
| `length` | 쪽·장·글자 수가 `length` 상한 안인가 | 모두 | 넘으면 `fail`. MD는 글자 수만 보고 쪽 기준은 `skip` |
| `r1_tables` | 표마다 첫 칸 글과 마지막 칸 글이 같은 쪽에 나오는가 | 모두 | 다르면 `warn` (의심 — 판정은 ⑦ 시각 검수). MD는 `skip` |
| `rewrite` | 결과 옆에 `<결과>.rewrite.hwpx`(`out.hwpx.rewrite.hwpx`) 또는 `<결과 이름>.rewrite.hwpx`(`out.rewrite.hwpx`)가 있는가 | HWPX | 있으면 `fail`: patch가 제자리 반영을 못 함. writer가 어느 파일이 결과인지 정해 보고 |

- **R6 정규화.** 비교 전에 `○`(U+25CB)·`ㅇ`(U+3147)·`ᄋ`(U+110B)·`◦`(U+25E6)를 같은 부호로, `•`·`·`를 같은 부호로 봅니다.
- **형식별 읽는 법.** DOCX는 python-docx(스타일·run 서식·표), PPTX는 python-pptx(레이아웃·플레이스홀더·run 서식), MD는 원문(제목 `#` 수준·목록 부호·표), HWPX는 zip 안 `Contents/section*.xml`의 `hp:t` 글과 `header.xml`의 글자·문단 모양 id입니다. HWPX의 R4·R5는 "견본이 쓰지 않던 글자·문단 모양 id를 결과가 참조하는가"로 판정합니다.
- 읽을 수 없는 항목(예: MD의 서체)은 `skip`과 이유를 남깁니다. 해당 모드·형식이 아닌 검사도 `skip`이며, `report.json`에는 13개 id가 언제나 모두 들어갑니다.

### 검사 세부

- **줄 머리 부호 (R6).** 문단 글의 첫 공백 앞 토큰이 부호 모양이면 줄 머리 부호입니다. 부호 모양은 기호 한 글자(`□ ■ ◇ ◆ ○ ㅇ ᄋ ◦ ● - – • · ※ ▶ ☞`)이거나 번호 모양(`1.` `1)` `(1)` `①` `1.1` `가.` `가)` `(가)` `A.` `A)` `Ⅰ.`)입니다. 한글 번호는 `가`–`하` 열네 자만 봅니다(`힣.`·`(힣)`은 부호가 아님). `(주)회사`·`(사) 협회`처럼 법인 약칭은 번호가 아닙니다. 번호 모양은 숫자·글자가 달라도 같은 부호로 봅니다(`3.` = `1.`). `○○사업`처럼 토큰이 기호 한 글자가 아니면 부호가 아닙니다. 네 자리 숫자로 시작하는 `2026.`·`2026.11.12.`는 날짜의 연도라 부호가 아닙니다(`profile_extract`도 같은 규칙). `structure.numbering` 항목도 같은 방식으로 모양을 정합니다. 부호가 없는 문단은 세지 않습니다. 수준은 DOCX (스타일, 왼쪽 들여쓰기), PPTX 문단 `lvl`, MD 제목은 `#` 수·그 밖 줄은 줄 앞 공백 수, HWPX 문단 모양 id로 묶고, 한 수준 안에 모양이 둘 이상이면 섞인 것입니다. MD 제목은 `#`와 공백을 뺀 글로 부호를 봅니다. `structure.numbering`이 있는데 글에 부호가 하나도 없으면 `skip`입니다 — DOCX 자동 번호(`numPr`)·HWPX 프리셋의 □·ㅇ은 문단 속성이라 글에 나타나지 않으므로, 「부호 없음」을 통과로 보지 않고 렌더로 확인합니다(⑦). `numbering`이 비어 있으면 「부호 없음」은 `pass`입니다.
- **스타일 이름 (R5).** DOCX는 문단 스타일 이름(표 칸 안 문단 포함)만 `styles_allowed`와 비교하고 표 스타일은 보지 않습니다. PPTX는 슬라이드 레이아웃 이름입니다. 서체·크기는 `design.type.*`의 `font`·`pt`, 색은 `design.color` 값과 비교하며, 토큰이 비어 있거나 값으로 쓸 수 없는 항목(`확인 못 함` 같은 글, 숫자가 아닌 pt)은 비교하지 않습니다. R4도 같아서, 토큰 값이 쓸 수 없거나 결과에서 값을 읽지 못한 항목은 비교에서 뺍니다. run에 직접 적힌 값만 봅니다(스타일에서 물려받은 값은 R4가 봄).
- **표 머리행.** 2행 이상인 표만 비교합니다(1행짜리 틀 표는 머리행이 없음). 머리행 서식은 첫 행 run들의 굵기와 칸 바탕색입니다.
- **분량 (`length`).** 문서 전체는 프로파일 최상위 `length`(`pages`·`slides`·`chars` 중 있는 것), 섹션은 `structure.sections[].length.chars`의 상한을 봅니다(form 모드는 섹션 분량을 보지 않고 최상위 `length`만 봅니다 — 양식 섹션은 문서 끝까지 이어져 글자 수가 양식 전체이기 때문입니다). `pages`는 렌더 쪽 수(`pages.json` 또는 `page_NNN.svg`·`page.svg` 수)이고, 렌더가 없으면 `skip`입니다. `lines`는 조판에 따라 달라 스크립트가 보지 않고 detail에 「⑦ 리뷰어 확인」으로 남깁니다.
- **빈칸 constraint.** `re:<정규식>`이면 칸 글 전체가 맞아야 합니다(fullmatch). 그 밖의 글로 쓴 constraint는 판정하지 않고 detail에 남겨 ⑦로 넘깁니다.
- **섹션 범위 (`scope`).** 결과에서 섹션 시작은 견본 anchor 문단과 같은 글의 문단으로 찾습니다. PPTX `sl:N`은 견본 N번째 슬라이드의 id(`p:sldId`)로 결과 슬라이드를 찾습니다. 그래서 슬라이드 복제·삭제로 순서가 밀려도 섹션 경계가 따라갑니다. 섹션 첫 슬라이드가 지워졌으면 그 섹션(다음 섹션 시작 장 앞까지, 다음 섹션이 `h:` anchor여도 견본에서 그 제목의 장으로 셈)의 남은 견본 슬라이드 가운데 결과에서 가장 앞선, 글이 있는 장을 시작으로 씁니다(남은 장이 없거나 모두 글 없는 장일 때만 「찾지 못함」). 단 `update.sections` 밖 섹션은 첫 슬라이드가 지워졌으면 대체 시작 없이 「찾지 못함」(scope fail)입니다 — 남은 장에서 시작하면 그 앞에 끼운 장이 편집 섹션에 묻혀 삭제가 숨습니다. 견본 id가 결과에 하나도 없으면(다른 프로그램이 다시 저장해 id를 새로 매긴 경우) 자리 N으로 찾습니다. `update.sections` 밖 섹션과 첫 섹션 앞 부분은 문단·표 칸 글의 순서가 견본과 같아야 합니다.
- **자리표시 위치.** `sN`·`fN`·`t:…` 칸 locator는 결과에서 그 범위 안을 찾습니다. `p:`·`sl:` 같은 dump locator는 편집으로 번호가 바뀌므로 문서 전체에서 찾습니다.
- **R1 표.** 표마다 첫 칸·끝 칸 글(`profile_extract.py tables`와 같은 규칙: 40자 자름, 빈 끝 칸은 그 행의 마지막 빈 아닌 칸)을 쪽별 글에서 공백을 빼고 찾습니다. 칸 글 전체가 한 쪽에 있어야 그 쪽으로 봅니다. 기호(`□`·`○`·`※` 등)가 든 칸은 렌더가 기호를 다른 글자로 바꿔 찍을 수 있어, 전체 글로 못 찾았을 때만 낱말 단위로 다시 찾습니다. 못 찾은 표는 detail에 적고 넘어갑니다. `locations`에는 의심 표의 `t:N`을 적습니다.

## 입력 파일

`.docu-writer/placeholders.yaml` (writer가 ⑤에서 씀):

```yaml
- locator: s2            # 설계서 §5 locator 문법: s2 · f1 · t:1/r:2/c:3 · p:12 · sl:3/ph:1/p:2
  expect: "총 ○○건"
  reason: 근거 없음      # 근거 없음 | 개인정보 | 비밀값
```

## 출력

`<out-dir>/report.json`은 검사 항목 표 순서대로 13개 `{id, status, detail, locations}`의 JSON 목록입니다. `status`는 `pass`·`fail`·`warn`·`skip`, `locations`는 locator 글의 목록입니다. 검사할 대상이 없으면 `skip`입니다: `--placeholders`가 없으면 `placeholder`, `length`가 없으면 `length`, `--pages-dir`가 없으면 `r1_tables`. 표준 출력에는 다음 요약을 냅니다.

```
### 문서 검증: <결과 파일>
- 결과: 통과 | 차단 (종료 코드 N)
  pass  hash          견본 sha256 일치
  fail  residue       3건: "2025년 상반기 실적" (2쪽) …
  warn  r1_tables     표 t:2 첫 칸 3쪽, 끝 칸 4쪽
  skip  r5_tokens     MD는 서체 정보 없음
```

`markup`·`r6_numbering`·`r1_tables`의 `detail`과 `locations`에는 결과 문서의 글을 적지 않습니다. 결과 글은 양식 값(이름·전화번호)일 수 있으므로 종류(`굵게 ** 2곳`), 부호 모양(`「1.1」`), 표·문단 위치(`t:2`, `p:3`, locator가 없으면 `문단 N`)만 냅니다. YAML 파일이 틀렸을 때도 오류 종류와 줄·열만 보이고 틀린 줄의 글은 보이지 않습니다.

## 실패했을 때

- **검사를 약하게 만들어 통과시키지 않습니다.** 프로파일의 `sample_text`·`styles_allowed`·`length`를 결과에 맞춰 고치는 것은 고친 것이 아닙니다. 프로파일이 틀렸다고 판단되면 고치지 말고 보고합니다(④ 승인으로 되돌림).
- **`residue`가 사실인 글을 잡았을 때**(예: 견본과 이번 판 모두에 맞는 끝난 일정): writer는 사실을 바꾸거나 지워서 통과시키지 않습니다. 메인 대화에 해당 지문과 근거를 보고하고, 메인 대화가 analyst에게 `sample_text` 수정을 맡긴 뒤 `profile_extract.py check`와 ④ 재승인(`approved.sha256` 다시 쓰기)을 거쳐 ⑥을 다시 돌립니다.
- R1·R2를 맞추려고 토큰(글자 크기·여백·줄 간격)을 바꾸지 않습니다. `design-review`를 따릅니다.
- 같은 실패가 세 번 반복되면 멈추고 원인과 함께 보고합니다.
